## 分析

### 为什么 512MB 退化、256MB 改善？

**512MB**: page cache 充裕 (file ~300MB)，合并后更大 readahead 窗口预读过多冷页，
挤占已有热页空间。8T -24% 最严重（竞争激烈但 page cache 尚多）。

**256MB**: page cache 极度紧张 (file ~20-50MB)，每个 syscall 的内核开销占比更大。
合并连续页减少了 syscall 数量（~10 pages -> ~3-4 merged），
内核 I/O 调度器批量处理更高效。

### FVC 命中率不受影响

FV_hit_rate 在 merge on/off 下一致（45.7% / 49.1%），符合预期（合并不改变搜索逻辑）。

## H2 条件性确认

- ✅ 256MB 12T+ 有显著收益 (+11~18%)
- ❌ 512MB 大多退化 (page cache 充裕时合并有害)
- **最佳应用场景**: 256MB cgroup 高并发
