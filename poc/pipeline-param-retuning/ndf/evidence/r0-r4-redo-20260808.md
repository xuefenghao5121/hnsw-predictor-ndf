## 核心发现

### 1. 基线验证通过
M=16 EF=100 实测 1,081 QPS vs CON-SLA-020 基线 1,076 QPS，差 0.5%（噪声范围）。
证明 L4_WILLNEED=1 + PAGE_MERGE_BG=1 的修正是正确的。

### 2. M=24 EF=60 是 1T Pareto 最优
- vs M=16 EF=80 (BASE 基线): +15.3% QPS (1T), +40.6% QPS (16T)
- vs M=16 EF=100 (旧默认): +36.5% QPS (1T)
- recall 96.60% ≥ 95% ✅

### 3. ADAPTIVE 模式效果惊人
M=24 EF=60 + ADAPTIVE: agg=2,543 QPS (1T)，比 BASE 模式 +72.3%。
比 DEC-086 最优 (M=16 EF=90 + ADAPTIVE, agg=1,388) 高 +83.2%。

### 4. PQ M=32 仍是唯一选择
M=16 recall 91.60% (不达标)，M=64 QPS 下降 31%。

### 5. Block size 32K 有显著优势
32K vs 64K: +52.5% QPS，recall 不变。旧 R4 (非严格) 结论是"无影响"，
严格 cgroup 下 32K 优势显现。需要进一步验证。

### 6. 旧 R0-R5 数据完全不可信
旧 R5 M=16 EF=100 1T: 146 QPS -> 新 R0': 1,081 QPS (7.4x 差距)
根因：缺少 L4_WILLNEED=1，与 DEC-070 记录的 17.7x 影响一致。

## Cgroup 监控数据 (CON-SLA-014 合规)

### 峰值内存

所有配置 `memory.peak = 268435456` (256MB) = cgroup limit，`oom = 0`，`violations = 0`。

> peak_bytes = limit 说明运行中 cgroup 内存达到上限，内核回收 page cache 以避免 OOM。
> 这是 DiskHNSW 在 256MB cgroup 下的预期行为（page cache 与 anon 内存共享预算）。

## R5.1: EF 细粒度扫描 (1T, BASE, 256MB)

###动机

R0' 粗扫发现 M=16 EF=60 QPS=2,594 但 recall=94.94% (差 0.06pp)。
在 EF=60-80 之间细扫以精确定位 recall ≥ 95% 的最低 EF。

同时下探 M=24 EF=50/55，看 M=24 能否进一步降 EF。

### 结果

| Config | Agg QPS | Steady QPS | Recall@10 | RSS (MB) |
|--------|---------|-----------|----------|---------|
| **M=16 EF=65** | **2,482.6** | **3,288.8** | **95.52% ✅** | 229 |
| M=16 EF=70 | 1,389.5 | 1,534.7 | 96.00% | 229 |
| M=16 EF=75 | 1,296.1 | 1,475.0 | 96.45% | 229 |
| M=24 EF=50 | 1,654.6 | 1,978.8 | 95.34% ✅ | 232 |
| M=24 EF=55 | 1,571.7 | 1,825.6 | 96.09% | 232 |

### 关键发现

1. **M=16 EF=65 是新 Pareto 最优**：QPS=2,483, recall=95.52%
   - vs M=24 EF=60 (之前最优): +64.4% QPS
   - vs M=16 EF=100 (旧默认): +127.4% QPS
   - recall 余量仅 0.52pp（95.52% vs 95%），需评估跨数据集鲁棒性

2. **EF=65->70 QPS 断崖**：2,483 -> 1,390 (-44%)
   - EF=65 时 I/O 量刚好在 page cache 预算内
   - EF=70 时 I/O 量突破临界点，page cache 开始 thrashing
   - 这是 DiskHNSW 独有的"内存预算再分配"效应

3. **M=24 EF=50 达标**：recall=95.34%, QPS=1,655
   - 但 QPS 远低于 M=16 EF=65 (1,655 vs 2,483)
   - M=16 在低 EF 区间全面优于 M=24
