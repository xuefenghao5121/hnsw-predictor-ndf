## 分析

### 512MB 12T 有收益 (+6.7%)

- perf profile 显示 12T WILLNEED 锁竞争占 6.27%
- 禁用后 +6.7% QPS, 与锁开销占比吻合
- **但仅限 12T 窗口**: 8T 锁竞争还不够大，16T+ page cache 需求压倒锁收益

### 512MB 16T+ 灾难性退化 (-38%)

- 16T+ 并发量更大, FineRerank pread 量更多
- 没有 WILLNEED 预读, pread 变回串行阻塞 I/O
- page cache 命中率下降 (无预读 -> 页未就绪 -> 同步等待)
- **WILLNEED 的 I/O 并行收益 >> 锁竞争损失 (在 16T+)**

### 256MB 全面灾难 (-30~50%)

- 256MB page cache 极度紧张 (file ~50MB)
- 每个页面都需要从磁盘读, WILLNEED 的 readahead 是核心机制
- 禁用 WILLNEED = 退回到串行 I/O -> QPS 砍半

## 结论: H6 部分确认

- ✅ 512MB 12T 有 +6.7% 收益 (锁开销 ~6.27% 被消除)
- ❌ 不能无脑禁用: 16T+ 和 256MB 下 WILLNEED 是核心 I/O 机制
- **最佳策略**: 仅在 512MB cgroup + 10-14T 窗口内禁用 (太窄, 不值得 promote)

### 根因

WILLNEED 有双重作用:
1. **I/O 并行化** (主要): readahead 让 pread 不阻塞 (所有场景都需要)
2. **内核锁竞争** (副作用): 仅在 12T+ 且 page cache 充裕时成为瓶颈

方向 B 的简单阈值策略无法区分这两种情况。需要更智能的自适应机制 (方向 A 后台线程化是正确方向)。
