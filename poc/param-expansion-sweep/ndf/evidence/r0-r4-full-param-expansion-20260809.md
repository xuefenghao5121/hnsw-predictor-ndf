## R0: FLAT_VEC_MB 扫描 (M=16 EF=65)

| FVC | Agg QPS | Steady QPS | Recall | RSS | vs FVC=64 |
|-----|---------|-----------|--------|-----|-----------|
| 32 | 1,411 | 1,563 | 95.52% | 197MB | -4.0% agg |
| **64** | **1,469** | **1,620** | **95.52%** | 229MB | baseline |
| **96** | **1,497** | **1,733** | **95.52%** | 253MB | **+1.9% agg, +7.0% steady** |
| 128 | **907** | 1,022 | 95.52% | 253MB | **-38.3% agg ⚠️** |
| 160 | **595** | 646 | 95.52% | 254MB | **-59.5% agg ⚠️⚠️** |

### 发现

- **FVC=96 是最优点**: agg +1.9%, steady +7.0% (热向量命中率提升)
- **FVC=128 断崖**: agg 暴跌 38%! page cache 被完全吃光 (RSS=253 ≈ cgroup 256MB)
- **FVC=160 崩溃**: agg 仅 595, page cache 为负 (anon > cgroup limit)
- **FVC=32 RSS=197MB**: anon 最小, page cache 理论最大, 但热向量命中率低拖累 steady
- **框架预测修正**: DEC-088 说 "大 FVC 伤害 agg" 正确, 但**最优点不在 64 而在 96**
- **根因**: FVC=96 时 RSS=253MB, page cache 仅 3MB (256-253), 刚好够 WILLNEED 预取窗口;
  FVC=128 时 RSS=253MB 但 page cache 已经在 OOM 边缘, 任何额外 file page 触发 thrashing

### FLAT_VEC_MB 内存预算公式

```
page_cache_available = cgroup_limit - RSS
RSS ≈ fixed_overhead (135MB init) + FVC + working_set
    ≈ 135 + FVC + (90 - 64)  [working_set grows with search]

FVC=64:  RSS ≈ 229, page_cache ≈ 27MB (10.5%) ✅
FVC=96:  RSS ≈ 253, page_cache ≈ 3MB  (1.2%) ⚠️ 边界
FVC=128: RSS ≈ 253+, page_cache < 0   → thrashing ⚠️⚠️
```

**结论: FVC=96 在 1T 下有效但无安全余量。多线程 (16T) 下可能不同（VisitedList 内存更大）。**

| 配置 | Agg QPS | Steady QPS | Recall | vs 基线 | ≥95%? |
|------|---------|-----------|--------|---------|-------|
| **基线 M=16 EF=65** | 1,486 | 1,640 | 95.52% | — | ✅ |

### 发现

1. **🏆 全局最优: M=24 EF=60 +ADAPTIVE(eef=35)**
   - agg=1,640 QPS / steady=1,931 QPS / recall=95.92%
   - vs DEC-091 基线 +10.4% agg
   - recall 安全余量 0.92pp

2. **M=16 EF=80 组合也强**: FVC=96 + EEF=35 + GAP=1.003 → agg=1,601, recall=95.69%

4. **R4b 过激**: GAP=1.003 + EEF=40 在低预算下 recall 跌破 95%
